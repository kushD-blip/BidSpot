## QC pass (2026-09-13) — bugs found and fixed
- **Bid modal isn't actually connected to the backend.** `handleBidSubmission()` in `js/ui.js` calls `state.addBid()` — pure client-side demo simulation. There's no Razorpay Checkout.js script tag anywhere in `index.html`, and nothing calls `/api/create-order` or `/api/verify-payment`. The API endpoints are correctly built and now have real test keys, but the frontend was never wired to them — clicking "Place Bid" today only ever updates the local demo dataset. This is the top item in Next batch below, not a small fix.
- **`state.USD_TO_INR` was `undefined` everywhere it was read.** `USD_TO_INR` is a module-level constant in `state.js`, never attached to the `state` object — but `js/ui.js` read `state.USD_TO_INR` in five places (preset chip math, the bid modal's live price breakdown, and — most seriously — `handleBidSubmission()`'s currency conversion). Placing a bid while in INR mode (the default currency for every new visitor) computed `amountUSD` as `NaN`, which would have corrupted that listing's rank. Fixed by aliasing `this.USD_TO_INR = USD_TO_INR` in the `StateManager` constructor.
- **INR/USD toggle looked broken.** Clicking USD correctly updated every displayed amount, but nothing ever toggled the `.active` class on the currency pill itself, so it still looked like INR was selected. Added `renderCurrencyToggle()` to `js/ui.js`, called from the main render loop, mirroring the existing pattern for category chips and the time-range pill.
- **Real mobile horizontal-overflow bug** (this is what you saw on your phone). Root cause: `.main-content` is a CSS Grid with `grid-template-columns: 1fr` on mobile — but grid items get an implicit `min-width: auto` floor (same mechanism as flexbox), so the `1fr` track was growing to fit an unshrinkable `.card-title` deep inside `.leaderboard-container` instead of respecting the viewport. Measured directly: the grid column was computing to `463px` on a `375px` viewport. Fixed at the actual source (`min-width: 0` on `.leaderboard-container` and `.sidebar`, the two grid items) plus the contributing flex-chain issue (`.card-title` / `.card-title-row` needed `min-width: 0` too, since flex items have the same default floor). Verified: `document.documentElement.scrollWidth` now exactly equals `window.innerWidth` at 375px — zero overflow.
- **Duplicate, conflicting `.main-content` rule** existed in both `css/main.css` and `css/leaderboard.css` with different margin values — `leaderboard.css` loads later so its copy silently won, making the `main.css` copy dead code. This kind of split is exactly what made the overflow bug hard to trace. Consolidated into one definition in `main.css`.
- Also found, not fixed (dead code, not a bug): `js/audio.js` (Web Audio sound effects) is never imported anywhere, and `state.soundEnabled` is never initialized or exposed via any UI toggle. Harmless as-is; flagging in case you want sound wired up later.

## QC pass #2 (2026-09-13) — reproduced the insightdrop.in report and found the real cause
- **The two category dropdowns didn't share a category list.** The hero form's `claim-category-select` offered Productivity/Ecommerce/Fintech/Startups/AI Tools/SaaS/Developer; the bid modal's `bid-category-select` offered Startups/AI Tools/Fintech/SaaS/Developer/Marketing/Crypto — a completely different set. Picking "Productivity" (the hero form's default) meant `catSelect.value = "Productivity"` in the bid modal silently matched no `<option>`, leaving the category **blank** with no error. Reconciled both selects to the same 8 categories from `schema.sql` (Productivity, Ecommerce, Fintech, Developer, AI Tools, SaaS, Crypto, Marketing — dropped the ad-hoc "Startups" that isn't a real category), fixed the "Select Category" placeholder option to have an empty `value` instead of secretly defaulting to Productivity, and hardened every `'Startups'` fallback in `js/ui.js`/`js/state.js` to `'Productivity'`.
- **This is the actual explanation for "didn't get any data of what I added."** The bid modal's Listing Title and Tagline inputs had hardcoded `value="TopSpot Rank #1 Spot"` / `value="The bidding house for website traffic"` baked into the HTML — not placeholders, real pre-filled values. Typing your URL into the URL field (which worked) did nothing to that separate Title field, so unless you noticed and manually cleared it, every submission was titled "TopSpot Rank #1 Spot" regardless of what you actually entered — which is exactly why insightdrop.in never visibly showed up anywhere except buried in the URL. Removed the fake `value` attributes from title/tagline/URL/amount in `index.html` so they're empty and rely on their `placeholder` text instead.
- Reproduced the full flow end-to-end after the fix (hero form → confirm modal → bid modal → submit) with `insightdrop.in` / "InsightDrop" / "AI Tools" / $17,011 — the resulting listing now correctly captures every field and renders at the right rank with the right amount.
- Also found and fixed the same fake-hardcoded-`value` bug on the Bidder Information fields (`contact-name`/`contact-email`/`contact-phone`/`contact-zip` in `index.html`) — they defaulted to a specific real name/email/phone, which was about to become load-bearing (see below, these now feed real Razorpay orders) and would have silently attributed every bid to that identity unless the buyer noticed and retyped it.
- **Why `categories` existed but was empty in Supabase (part 1):** the SQL Editor commits each statement individually rather than wrapping the pasted script in one transaction, so a failure partway through leaves everything before it committed. Re-running the original (non-idempotent) script then failed immediately on `relation "categories" already exists` before it ever reached the `insert`. Rewrote `schema.sql` to be fully idempotent (`create table if not exists`, `on conflict do nothing` on the seed insert, `create index if not exists`, `drop policy if exists` before each `create policy`) — it's now safe to run the whole file again regardless of how far a previous attempt got.
- **Why it was still empty after that (part 2):** `select count(*) from public.categories` confirmed the 8 rows really were there — the anon-key REST check returning `[]` was a visibility problem, not a missing-data problem. Newer Supabase projects enable Row Level Security by default on every new table, including `categories` — and `schema.sql` only ever added RLS policies for `listings` and `bids`, never `categories`. With RLS on and zero policies, the anon key legitimately sees nothing. Added an explicit `public read categories` policy (`for select using (true)` — it's non-sensitive public metadata, no restriction needed) to `schema.sql`.

## Live wiring (2026-09-13) — the bid flow is now real, not a demo simulation
Decision made with you first: since `listings` is empty, the homepage now shows an
honest empty state ("No one's claimed a spot yet — Claim Rank #1") instead of either
staying on fake demo data or inventing placeholder listings. No fabricated vanity
numbers either — "Active Bidders," volume, and product count all show real values
(0 until real traffic exists), not the old hardcoded demo stats.

What changed:
- **`js/state.js`**: when Supabase is configured, the constructor starts empty (no demo seed, no fake stats/activity feed) instead of loading `INITIAL_LEADERBOARD`. New `loadFromSupabase()` fetches real listings + categories and maps each row into the shape the UI already expects (paise → rupees → USD, category joined by name, relative timestamps, a deterministic logo color from the row id). `getLiveStats()` no longer applies the old "minimum 15 active bidders" floor when live.
- **`js/app.js`**: calls `state.loadFromSupabase()` on startup and subscribes to realtime listing changes (`subscribeToListingChanges`) so other visitors' bids show up without a refresh.
- **`js/ui.js`**: `handleBidSubmission()` is now async and does the real thing — creates a `pending` listing in Supabase (or reuses the real id of an existing card being outbid, threaded through `openConfirmRankModal` → `openBidModalWithData` via the `data-outbid-id` that was already on the DOM but never read), calls `/api/create-order`, opens real Razorpay Checkout, calls `/api/verify-payment` on success, then reloads the board. Submit button disables while a payment is in flight. Empty-board leaderboard now shows a real CTA button ("Claim Rank #1") that scrolls to and focuses the hero form.
- **`index.html`**: added the Razorpay Checkout.js script tag; removed the fake hardcoded `value`s on the Bidder Information fields (same bug class as the listing title, but here it would've attributed real payments to a stranger's name/email).
- **`api/create-order.js`**: there's no admin approval queue, so a brand-new `pending` listing needs to be payable immediately — relaxed the status check to allow anything except `rejected`/`removed` (was: only `approved`).
- **`api/verify-payment.js`**: a `pending` listing now flips to `approved` automatically the moment its first payment verifies — this is what actually makes a new submission go live, since nothing else will.
- **`schema.sql`**: found via live testing that the `listings` insert policy for anon submissions never actually existed in your database (same partial-execution issue as the categories one) — gave you the isolated fix to run.
- **`js/supabase-client.js`**: `submitListing()` now generates the row's UUID client-side instead of reading it back after insert — a freshly-inserted `pending` row isn't covered by the public-read policy (only `approved` is), so the old `.select().single()` right after insert would fail under RLS even though the write itself succeeded.

### QC pass #3 — a real security bug, and a wrong assumption about what "outbid" means
- **Stored XSS, not hypothetical.** Listing title/tagline are real user input now (via `submitListing()`), and they were being inserted into `innerHTML` across five files without escaping — a malicious submitter's title could execute for every visitor viewing any leaderboard page. This wasn't a risk before today (the demo dataset was hardcoded), but it's a live vulnerability now that strangers can submit their own text. Added `escapeHtml()` to `listing-mapper.js` and apply it once, at the source, inside `mapSupabaseListing()` — every page automatically gets safe values without each having to remember to escape. Verified with actual `<img onerror=...>` / `<script>` payloads that they render as inert text.
- **Wrong assumption, caught before it shipped further:** I initially had "Outbid #1" reuse the existing listing's real database id — meaning clicking outbid on Postman's card would have added your money to *Postman's own total* instead of creating your own competing listing. That's backwards; outbid.lol's actual model (and the only sane reading of "claim this rank") is that outbidding pre-fills a **new** listing form with the target's name as an editable suggestion, and submitting always creates your own row. Fixed in `js/ui.js`: `openBidModalWithData` now takes a `prefillTitle` that's only set when the action came from an existing card (not from a fresh hero-form submission, which stays blank), and `handleBidSubmission` always calls `submitListing()`.

## Fixes from live testing (2026-09-13, round 4)
Six items you flagged from actually clicking around; all code-side fixes are done.

1. **Minimum bid was showing ₹8,925 on an empty board instead of ₹100.** Real bug, not cosmetic: `getMinBidForRank1()` had a leftover demo constant (`100` as a raw *USD* fallback, `+5` flat increment) that made sense when the seed dataset bid in thousands of dollars, but was nonsense once real bids start at ₹100. Fixed in `js/state.js`: empty board now correctly suggests the real ₹100 floor, and outbidding an existing top bid increments by 1% of it (floored at ₹10) instead of a flat, meaningless "+5". The hero's +/- buttons now step the same way and can't go below ₹100.
2. **A second, sneakier bug underneath #1:** even after fixing the constants, INR mode showed ₹85 instead of ₹100 for that same suggested minimum. Root cause: the internal currency conversion rounded ₹100 → $1 → ₹85 (a lossy round-trip that was invisible at demo-dataset scale but very visible at ₹100 scale). Fixed by keeping the USD-INR conversion unrounded internally and only rounding for display — the round-trip is now exact.
3. **Payment amount tampering — hardened, not just reassured.** The Razorpay integration was already secure the way it's built (the checkout amount is locked to a server-created order, and `verify-payment.js` only ever credits the amount stored in *our own* database record, never anything the client sends) — but added a second independent check anyway: `api/verify-payment.js` now re-fetches the payment directly from Razorpay's API and confirms the captured amount matches the order before crediting anything, in case of any future edge case.
4. **"Unexpected token" error on the payment step.** Root cause: `.json()` was called on the `/api/create-order` and `/api/verify-payment` responses unconditionally — if the endpoint isn't actually reachable (exactly what happens against the local static-file preview, which returns an HTML 404 page instead of JSON), parsing that HTML as JSON throws a raw `SyntaxError: Unexpected token '<'`. Added `parseJsonResponse()` in `js/ui.js` so a non-JSON response now surfaces a real message ("Server returned an unexpected response...") instead of a cryptic parser error. This will only ever have been visible against the local preview or a broken deployment — a working Vercel deployment returns real JSON from `/api/*`.
5. **Favicon added** — a small maroon gavel icon (matching the brand mark), added to all 10 pages as an inline SVG data URI (no extra file needed).
6. **Header now blends into the page** instead of sitting in a separate glass/blurred bar with a visible border — same background color, bigger padding, bigger logo — matching the reference look.

**Categories page** rebuilt to match the outbid.lol reference: a "Most active categories" spotlight panel (top 3 by volume, hidden automatically when nothing has bids yet) above a full grid, and each category card now shows its own top-3 mini-ranking instead of just a single leader line. Also **expanded the category list from 8 to 17** (added SEO & Visibility, Design & Creative, Business & Finance, Security & Privacy, Health & Wellness, Social & Creator Tools, Hiring & Careers, Education & Learning, Agencies & Services), updated in `schema.sql` and both category `<select>` dropdowns in `index.html`.
